Explain the difference between SAML and OAuth. When would a company choose one over the other?

SAML is an open authentication protocol usually used for office environments, where the user must log on to access a part of the system. Examples which companies might use SAML in are Microsoft 365 Sign in, Salesforce a customer management application, etc. Usually these application authenticated with SAML are part of the company's intranet in which the user verifies their identity. Network admins can manage users from a central location and specify what that user can access.

OAuth is an open authentication framework to give limited access to user's data to verify their identity without exposing passwords. OAuth uses third-party API to verify the legimacy of the user when authenticating. Usually OAuth is used in mobile apps, APIs and small web applications. To secure micro services, enable third-party integrations or to save on bandwidth compared to SAML.

OAuth is ofter used for outside the network connections in which you need to verify the user with a trustworthy API like Meta, Github or etc. SAML is used for more inside the network connections to verify user's identity with passwords.

Explain what a peer-to-peer VPN (for example n2n) is used for, and how it differs from a traditional site-to-site VPN.

A peer-to-peer VPN creates a direct connection to different nodes included in the network vs. a traditional site-to-site VPN connects two or more fixed networks together throught a centralized gateway router.

Some P2P VPNs use cases are for: remote workers so they can access their workstations, IoT devices when managing them so the don't have to expose port to the public and getting around CGNAT or NAT configs like movile networks, public Wi-Fi or home internet. This last one I have experience with using a modem and trying to play video games with a friend but the NAT settings don't allow port forwarding so we used ZeroTier.

While a traditional site-to-site VPN connects two fixed networks (e.g. an office and a data center) through a small number of gateway devices, with all traffic between the two sites routed through those gateways - a hub-and-spoke or point-to-point topology decided at configuration time.

What is a Web Application Firewall (WAF) and what kinds of attacks does it defend against? Where would you place one in the three-container architecture you built in Week 4 (Route → frontend → backend → db)?

The Web Application Firewall (WAF) exists between the client and a web applciation and inspects HTTP(S) traffic at the application layer. WAF looks for suspicious patterns that match already known attacks.

WAF is deployed in the very front of the application between the public internet and frontend application. On Rahti it is Plced in from on the Route and checks all external request before they get to the Nginx/Nodejs Fronend in my case.

List of different attacks WAF defends against.
  • SQL Injections
  • Cross-site scripting
  • Cross-site request forgery
  • Request-based DDoS
  • Known bad signatures

What is YAML and why has it become the default configuration format for Kubernetes/Rahti manifests? Compare it briefly to JSON.

YAML ("YAML Ain't Markup Language") is a human-written configuration management and DevOps tooling model with comment support, multi-document streams (Allows you to create multiple related objects in one deployment) and clear readability with it's Python-like indentation.

YAML is usually slower to parse due to it's more advanced logic than JSON. YAML has native comment support while JSON does not. JSON is used for machine-to-machine data tranfers and web APIs while YAML is used for humanmade configuration files. Every valid JSON document is also valid YAML; YAML is a strict superset of JSON.

Reflection

The biggest reliability concern is the dependency on a public API and the possibility of being rate limited from the service or failure of the lyrics backend service if many users use the application.

Without the WAF from Rahti the application could be left vulnerable to exploit scanners, XSS via input form attacks and even SQL injection attempts discussed in part A.

Hypothetically if I had used Redis to save the lyrics for a longer time reducing lookups from the public API it could have helped with the risk of being rate limited with little to no problem with cache invalidation because they can be cached long time as song lyrics are rarely changed after release.

Using Redis for the MySQL could be problem due to the time being looked up constantly by the client, it would not update every second if Redis was used.

Application did not use OAuth or Redis.
